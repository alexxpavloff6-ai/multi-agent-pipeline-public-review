По запросу пользователя проведён разбор репозитория [`can1357/oh-my-pi`](https://github.com/can1357/oh-my-pi) (команда `omp`, сайт [omp.sh](https://omp.sh/)) по аналогии с разбором Orca. Документ фиксирует архитектуру oh-my-pi, критику сообщества и сопоставление с текущим проектом.

## 2. Что такое oh-my-pi

oh-my-pi (`omp`) — терминальный AI-кодинг-агент, форк фреймворка **Pi** (оригинальный автор — Mario Zechner, `badlogic`). Развивает **Can Bölük (`can1357`)** — известный реверс-инженер и low-level разработчик (Windows kernel, NtLua, статический анализ).

Метрики на 15 июля 2026 года: ~17 900 звёзд, ~1 600 форков, ~120 контрибьюторов, создан 31 декабря 2025 года (~6,5 месяцев), активная разработка (релизы по несколько раз в день, v16.5.2 от 14 июля). Лицензия MIT.

Стек: TypeScript (Bun monorepo) + **нативный Rust-движок** через NAPI (`crates/omp-tools`, `crates/omp-core`) + Python-компонент (`python/robomp/web`). Это не «чистая обёртка» над чужой системой — omp самостоятельный агент с собственным скомпилированным ядром для тяжёлых операций.

Слоган сайта: *«a coding agent with the IDE wired in»* — акцент на LSP/DAP-интеграцию (настоящий отладчик lldb/dlv/debugpy, а не print-statements).

## 3. Принцип работы — архитектура

Архитектура многоуровневая. Ключевое наблюдение для текущего проекта: **детерминированное управляющее ядро — основное.**

### Три уровня управления

**Уровень 1 — низкоуровневый цикл `agentLoop`.** Классический function-calling цикл: LLM генерирует tool-calls → они исполняются → результат возвращается в контекст → новая итерация. Параллельное исполнение инструментов (`toolExecution: "parallel"`), хуки `beforeToolCall`/`afterToolCall`.

**Уровень 2 — `AgentHarness` (оркестрация).** Управляющий слой с **детерминированным конечным автоматом фаз**:

```typescript
type AgentHarnessPhase = "idle" | "turn" | "compaction" | "branch_summary" | "retry";
```

Структурные операции требуют `phase === "idle"` и синхронно выставляют фазу. Попытка запустить вторую операцию в занятом состоянии отклоняется с `AgentHarnessError code "busy"`. **LLM управляет только содержательной частью внутри фазы `turn`**; все структурные переходы — детерминированный TypeScript/Rust-код.

**Уровень 3 — подагенты (subagents).** Роли: scout (разведчик), planner (планировщик), reviewer (рецензент), worker (исполнитель). Паттерны: одиночный агент, fork контекста, параллельное выполнение, цепочки, фон-асинхронные цепочки, fan-out/fan-in, **изоляция через git worktree**.

### Ключевые инженерные решения

**Hash-anchored edits** — правки привязываются к хэшу состояния файла, что даёт детерминированную проверку корректности применения (защита от race condition при изменении файла между чтением и записью). Инженерный подход «как в контроле версий», не наивная строковая замена.

**Plan Mode** — режим планирования, где инструменты редактирования отключены, bash ограничен allowlist'ом. План — todo-список с уникальными ID; агент помечает пункты `[DONE:id]`; **состояние todo персистится между сессиями**.

**Compaction** — сжатие контекста через LLM-суммаризацию. Lossy, но полная история сохраняется в JSONL и доступна через `/tree`. Триггеры: ручной `/compact`, порог, переполнение. Авто-retry: при overflow ход прерывается, запускается compaction, затем ход повторяется.

**Sandbox** — расширение с `network`/`filesystem` ограничениями. Поддержка только darwin/linux; на Windows отключается с предупреждением, не крашит сессию.

**Hindsight memory / time-traveling** — история представлена как дерево веток диалога; можно вернуться к любой точке через `navigateTree`, `getBranch()`.

## 4. Критика сообщества

### Техническая критика

1. **Раздутый системный промпт (~40k токенов)** — топ открытая претензия (issue `#1734`, 13 реакций). Критично для локальных моделей: *«40k system prompt probably does more harm than code with local models»*. Пользователи называют его «Oh-my-bloat».
2. **Краши при обновлении и нативный код** — серия регрессий, связанных с Rust/FFI: краши при старте после апгрейда (`#651`, `#116`), SIGILL на CPU без AVX2 (`#672`), проблемы ARM64 (`#727`), Windows-краши.
3. **Точность edit-tool** — boundary-edge-cases портят файлы, stale-hash-детекция блокирует легитимные правки (`#2885`).
4. **Windows/TUI-регрессии** — MCP stdio открывает видимое окно консоли (`#3519`), стриминг невидим до resize (`#1534`), краш при вводе `@` (`#601`).

### Безопасность — самая принципиальная критика

**Issue `#3293`:** omp **не имеет path-scoped одобрений**; по умолчанию работает в `yolo`-стиле.

> *«it didn't have an approval feature... which is incredibly questionable from a security point»*

Бот `roboomp` спроектировал решение, но почти месяц ждёт решения мейнтейнера (статус `accepted`, без движения). Сравнение не в пользу omp: *«Goose treats security properly»*.

### Организационная критика

1. **Vouch-система** — PR от невouched автора закрываются автоматически; публичный файл `.github/VOUCHED.td`. Сейчас 126 vouched, 0 denounced. Обсуждается как «zero-cost fallacy of OSS in agentic era».
2. **Доминирование бота `roboomp`** в триаже — почти всё обсуждение в issues ведёт бот; человеческое участие мейнтейнера минимально. Риск bottleneck по безопасности и roadmap.
3. **Философский раскол с Pi** — *«people pushing oh-my-pi seem to have missed the point of pi... Downloading 200k+ lines of additional code seems completely against the philosophy»*.

### Что хвалят

Reddit r/LocalLLaMA: *«the best coding harness that's slept on»*, *«imo better than claude-code and qwen-code»*, *«extremely hackable with sensible defaults»*. Особенно ценят DAP/LLDB-интеграцию (killer-feature для low-level разработчиков), hashline-едиты, мультипровайдерность.

### Фактчек-уточнение

HN-комментарий *«Written by a person who is infamously annoying open source maintainers with AI slop PRs (see the DWARF debacle in OCaml)»* — **ошибочная атрибуция**. «DWARF debacle in OCaml» — это история Joel Reymont (`joelreymont`), не can1357. Этот комментарий — недостоверная персональная атака, не установленный факт.

## 6. Что полезного для текущего проекта

С учётом выбранного пути C (компоненты добавляются только по измеренным ошибкам), находки разделяются на две категории.

### Концептуальные подтверждения (усиливают принятые решения, не требуют действий)

1. **Детерминированный конечный автомат фаз** — omp использует `idle/turn/compaction/branch_summary/retry`, текущий проект — состояния проект→запуск→задание→попытка. Тот же принцип: LLM не управляет переходами.
2. **Hash-anchored edits** — omp привязывает правки к хэшу файла; текущий проект привязывает результаты к SHA-256 контрактов. Та же инженерная идея — детерминированная проверка через хэши.
3. **Plan Mode с персистентным todo** — близко к подходу проекта: план не исчезает между сессиями, состояние сохраняется.

### Идеи для будущего (после измерения ошибок по пути C)

Эти идеи полезны, но не сейчас — путь C требует сначала измерить ошибки, потом добавлять компоненты:

1. **Compaction стратегия.** При переполнении контекста (длинные ГОСТы, договоры) подход omp (lossy summary + полная история в JSONL + дерево веток) — рабочий вариант. Добавлять только когда проблема измерена.
2. **Дерево веток диалога (time-traveling).** Возможность вернуться к любой точке и пойти другим путём — полезно для исследования альтернатив. Усложнение, оправданное только при реальной потребности.
3. **Subagent-паттерны (fan-out/fan-in, цепочки).** Когда граф задач вырастет за пределы 2–3, паттерны omp (parallel, chain, worktree-изоляция) — референс. Расширять только по необходимости.

### Уроки от критики (что не делать)

1. **Не раздувать системный промпт.** 40k токенов omp — главная техническая претензия. Промпты GLM/DeepSeek должны быть минимальными.
2. **Не работать без одобрений по умолчанию.** Yolo-стиль omp — главная критика безопасности. Текущий проект строже (двухфазные подтверждения D-181), это подтверждает правильность подхода.
3. **Не замыкать триаж на боте.** Доминирование `roboomp` создало bottleneck по безопасности. Человек в цикле обязателен для ответственных решений.
4. **Не пренебрегать Windows-совместимостью.** Краши omp на Windows — напоминание, что Windows-специфика проекта (AppContainer, наблюдатель процессов) оправдана.

## 7. Сопоставление с Orca

oh-my-pi — третье внешнее подтверждение детерминированного ядра после Orca и Anthropic. Сравнение трёх:

| Критерий | Anthropic | Orca | oh-my-pi |
|---|---|---|---|
| Тип источника | Engineering-блог | Продукт (YC, 18,8k★) | Продукт (6,5 мес, 17,9k★) |
| Управляющее ядро | Рекомендация | Детерминированный polling-цикл | Детерминированный конечный автомат фаз |
| Роли | workflows/agents | Coordinator + Workers | scout/planner/reviewer/worker |
| Изоляция | — | git-ворктри | git-ворктри + sandbox |
| Одобрения | Рекомендация | Decision gates | **Отсутствуют по умолчанию (yolo)** |
| Главная критика | — | утечка PTY, война токенов | раздутый промпт, yolo-безопасность |

**Общий вывод трёх разборов:** лидеры рынка (Orca, oh-my-pi) приходят к детерминированному ядру, но спотыкаются о разные слабые места — у Orca это изоляция процессов и аутентификация, у oh-my-pi — раздутый промпт и отсутствие одобрений. Текущий проект проектирован против обоих классов проблем изначально.

## 8. Главный вывод

oh-my-pi — третье внешнее подтверждение ключевого решения проекта (детерминированное ядро), после Anthropic и Orca. Бэкграунд can1357 в RE/низкоуровневом программировании проявляется в инженерной строгости (Rust-движок, hash-anchored edits, аккуратная работа с процессами) — это близко к философии SHA-256-верификации текущего проекта.

Но oh-my-pi — другой класс системы: самостоятельный кодинг-агент с subagents, тогда как текущий проект — конвейер для аналитических задач с доказательной основой. Прямое заимствование архитектуры некорректно. Полезны отдельные идеи (compaction, дерево веток, subagent-паттерны), но по пути C они добавляются только после измерения соответствующих ошибок.

Главная ценность разбора — уроки от критики oh-my-pi: не раздувать промпты, не работать без одобрений, не замыкать триаж на боте. Текущий проект уже избегает этих ошибок, и разбор подтверждает, что его строгость оправдана.

## 9. Статус и место в проекте

Документ является исследовательским сравнением и не меняет состав `PRJ-PILOT014` или `RUN-014`, не разрешает внешние вызовы и не переносит денежные пределы. Заимствования из oh-my-pi ограничены совместимыми идеями (compaction, дерево веток, subagent-паттерны) и применяются только по пути C — после измерения соответствующих ошибок. Проверка по D-150 остаётся будущим этапом.

### А.8. Главный вывод таблицы

Все три проекта пришли к детерминированному управляющему ядру — это сходство, подтверждённое тремя внешними источниками (Anthropic, Orca через D-215, oh-my-pi через D-232). Но системы решают разные задачи и спотыкаются о разные слабые места:

- **Orca** — сильна в параллельном кодинге, но проваливается в изоляции процессов и аутентификации (утечка PTY, война токенов).
- **oh-my-pi** — сильна в IDE-интеграции (LSP/DAP) и инженерной строгости (Rust, hash-anchored edits), но проваливается в одобрениях (yolo) и раздувает промпт.
- **Текущий проект** — проектирован против обоих классов проблем изначально (строгая изоляция, обязательные одобрения, минимальные промпты), но платит за это скоростью: 35–40% готовности против 17–18 тыс. звёзд у конкурентов.

Строгость текущего проекта — не перестраховка, а оправданный выбор именно в свете того, во что превращается оркестрация без неё. Сравнение трёх систем это подтверждает.
