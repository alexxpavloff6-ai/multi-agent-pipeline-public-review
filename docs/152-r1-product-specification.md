# Единая спецификация рабочей версии R1

> **Примечание к публичной редакции.** Связи внутри комплекта 149–157 и внешние
> официальные либо научные источники сохранены. Ссылки на закрытые запуски,
> местные пути, внутреннюю память, код и материалы вне комплекта заменены
> текстовыми указателями; соответствующие закрытые файлы не опубликованы.

**Редакция:** 1.0

**Дата:** 22 июля 2026 года

**Состояние:** нормативный проект для реализации в ветке `main`; не является
разрешением на изменение программы, создание RUN или обращение к моделям

**Область:** один полезный последовательный цикл
Codex App → Hermes Agent → Codex App → Claude Code → Codex App → пользователь

## 1. Назначение документа

Настоящая спецификация переводит требования
[PRD](149-product-requirements-document.md),
[целевой архитектуры](150-current-target-architecture-and-prd-traceability.md)
и [паспортов частей](151-component-passports.md) в один проверяемый договор
рабочей версии R1. Документ определяет:

1. единый неизменяемый план RUN Д24 и одно решение пользователя;
2. вход, постановку и критику Codex;
3. полезный доказательный модуль Hermes;
4. принятую совокупную основу;
5. полную роль Claude Code;
6. сквозную цепочку доказательств и качества;
7. один точный полезный сценарий;
8. состояния, остановку, восстановление и местные проверки;
9. границу между настоящей документацией и будущей реализацией.

Спецификация не добавляет новые роли, не расширяет компактный автомат
состояний и не объявляет R1 достигнутой. R1 появляется только после реализации
этого договора, прохождения местных проверок и одного принятого полезного
цикла на реальных входах.

## 2. Нормативные слова и идентификаторы

Слова **обязан**, **запрещено** и **допускается** задают обязательное,
запрещённое и разрешённое поведение. Слово **кандидат** означает, что связка
ещё не доказана для полной роли R1.

Требования имеют устойчивые идентификаторы:

- `R1-PLAN-*` — единый план RUN;
- `R1-CODEX-*` — вход, постановка и критика Codex;
- `R1-HERMES-*` — полезные модули Hermes;
- `R1-BASE-*` — принятая совокупная основа;
- `R1-CLAUDE-*` — полная роль Claude Code;
- `R1-QUALITY-*` — качество и доказательства;
- `R1-OPS-*` — состояния, остановка и восстановление;
- `R1-SEC-*` — безопасность и изоляция;
- `R1-TEST-*` — местная проверка.

Имена будущих договоров и полей в этом документе задают целевой смысл. Их
точная схема JSON и команды ядра создаются в `main` отдельным изменением и не
считаются реализованными только из-за наличия настоящей спецификации.

## 3. Граница R1 и критерий успеха

### 3.1. Что входит

R1 включает один точный контур:

1. пользователь передаёт полезную задачу и материалы через Codex;
2. Codex формирует неизменяемую спецификацию и критерии;
3. ядро регистрирует один RUN и заранее известный последовательный граф;
4. Hermes создаёт несколько ограниченных доказательных модулей;
5. Codex отдельно принимает каждый модуль и совокупную основу;
6. Claude Code получает только принятый неизменяемый архив и создаёт полный
   итоговый документ;
7. Codex критикует точную редакцию итога;
8. ядро готовит отчёт, пользователь принимает или отклоняет результат.

### 3.2. Что доказывает успех

`R1-SCOPE-001`. Успех доказывает, что одна закреплённая конфигурация способна
выполнить один реальный полезный цикл с сохранением состояний, доказательств,
ограничений и расхода.

`R1-SCOPE-002`. Успех не доказывает переносимость на другой компьютер,
превосходство над одной сильной моделью, пригодность других моделей или
универсальность для других предметных областей.

`R1-SCOPE-003`. Технический успех отдельной попытки, искусственная проверка или
непринятый итог не являются успехом R1.

### 3.3. Что не входит

В R1 не входят D-150, автоматический выбор моделей, RAG, ретривер,
самообучение, память опыта, би-темпоральный индекс, автоматическая установка,
переносимый выпуск R2, автоматические повторы и прямое общение моделей.

## 4. Полномочия и единственный владелец состояния

| Участник | Полномочия | Не имеет права |
|---|---|---|
| пользователь | цель, утверждение плана, принятие отчёта, разрешение новой редакции | менять архив попытки или переносить старое разрешение |
| Codex App | постановка, критерии, разбиение, содержательная критика, проект решения | напрямую менять SQLite, разрешать расход вместо пользователя, принимать себя в D-150 |
| ядро | состояния, очередность, допуск, пределы, архивы, события, остановка | принимать смысловые решения вместо человека или оценщика |
| Hermes Agent | ограниченное извлечение, сопоставление и анализ доказательств | менять цель, выполнять итоговый синтез, запускать следующую роль |
| Claude Code | полная оценка принятой основы и итоговый документ | получать непринятые черновики, принимать свой итог, закрывать RUN |
| подсистема выбора | объяснимая рекомендация связки | переключать модель, разрешать вызов, владеть состоянием |

`R1-AUTH-001`. Только детерминированное ядро изменяет официальные состояния.

`R1-AUTH-002`. Модели не общаются напрямую: любой переход идёт через
запечатанный договор, техническую проверку, архив и отдельный содержательный
шлюз.

## 5. Д24 — единый неизменяемый план RUN

### 5.1. Назначение

Д24 заменяет серию подтверждений каждого отдельного вызова одним осознанным
решением пользователя по всему RUN. Проектное имя договора —
`run_execution_plan`.

`R1-PLAN-001`. До первой попытки ядро обязано запечатать точную редакцию Д24,
вычислить её канонический SHA-256 и показать пользователю понятное резюме.

`R1-PLAN-002`. Одно подтверждение пользователя действует только на один
`project_id`, один `run_id`, одну редакцию Д24, до заданного срока и в пределах
закреплённого числа вызовов и ресурсов.

### 5.2. Обязательные группы полей

| Группа | Обязательное содержание |
|---|---|
| идентичность | тип договора, версия схемы, `artifact_id`, редакция, `project_id`, `run_id`, время создания и срок действия |
| цель | полезная цель, язык, предметная область, ожидаемый итог, неизменяемая ссылка и SHA-256 спецификации |
| граф | все задания, зависимости, роль, порядок, входы, выходы, критерии и условия открытия |
| связки | модель, поставщик, оболочка, версии, режим, сетевой путь, хеш проектной настройки и договор средств для каждой роли |
| ресурсы | предел входа, выхода, времени и попыток; число обращений поставщика по роли и суммарно; денежный потолок и подлимиты |
| качество | обязательные критерии, запрещённые сокращения, условие полного результата и правило честного отказа |
| доказательства | допустимый состав источников, способ фиксации редакций, ссылки, SHA-256 и границы выводов |
| остановка | технические и содержательные причины остановки, запрет скрытого повтора, порядок преемника и подъёма сложности |
| решение | точная фраза подтверждения, SHA-256 плана, время, источник решения и срок его действия |

`R1-PLAN-003`. Граф обязан содержать все плановые модельные обращения. Скрытый
служебный вызов, вспомогательная модель и обращение оболочки к поставщику
считаются вызовами и входят в общий предел.

`R1-PLAN-004`. Денежный предел является предохранителем. При приближении к нему
запрещено молча сокращать критерии, вход или выход. Вызов блокируется до новой
редакции плана, если достаточный качественный результат в прежних пределах
невозможен.

`R1-PLAN-005`. Неиспользованный остаток денег, времени, вызовов или попыток не
переносится в другой RUN и не разрешает замену связки.

### 5.3. Жизненный цикл Д24

Жизненный цикл плана является состоянием договора, а не расширением автомата
проекта, RUN, задания или попытки:

`draft → sealed → approved → active → exhausted | expired | superseded | closed`.

- `draft` можно редактировать;
- `sealed` имеет канонический SHA-256 и больше не меняется;
- `approved` связан с точным решением пользователя;
- `active` разрешает только предусмотренные действия;
- `exhausted` означает исчерпание хотя бы одного жёсткого предела;
- `expired` означает истечение срока;
- `superseded` указывает на новую редакцию, не наследующую разрешение;
- `closed` означает окончание соответствующего RUN.

`R1-PLAN-006`. Повтор того же подтверждения идемпотентен. Подтверждение другого
SHA-256, другого RUN или истёкшего плана отвергается.

`R1-PLAN-007`. После первого внешнего вызова план нельзя отменить так, будто
расхода не было. Он может быть остановлен с сохранением уже случившихся
событий и неполных сведений расхода.

### 5.4. Значимое изменение

`R1-PLAN-008`. Новая редакция и новое решение пользователя обязательны при
изменении цели, спецификации, графа, входного архива, критерия, связки,
настроек рассуждения, сетевого пути, средств, числа вызовов, срока, денежного
или технического предела, правила повтора, остановки либо подъёма сложности.

Исправление орфографии в поясняющем резюме допускается без новой редакции,
только если каноническое содержание Д24 и его SHA-256 не меняются.

## 6. Договор входа и постановки Codex

### 6.1. Вход пользователя

`R1-CODEX-001`. Входной пакет обязан содержать:

- исходную формулировку и ожидаемое практическое применение;
- язык, предметную область и целевую аудиторию;
- локальные файлы и внешние ссылки с допустимым способом чтения;
- обязательные и исключённые источники;
- ограничения безопасности, конфиденциальности и внешних действий;
- ожидаемый вид, объём и структуру результата;
- известные неизвестные и решения, требующие пользователя.

Секреты не входят в пакет. Неподдерживаемый файл или недоступная ссылка
фиксируются до исполнения, а не заменяются догадкой.

### 6.2. Спецификация задачи

`R1-CODEX-002`. Codex обязан до исполнения создать запечатанную спецификацию,
в которой каждый обязательный критерий имеет идентификатор, способ проверки,
критичность и связь с ожидаемым разделом результата.

`R1-CODEX-003`. Разбиение обязано сохранять роль Hermes низовым
исполнительским слоем: один модуль имеет один предмет, ограниченный набор
источников и законченный проверяемый выход, но не подменяет итоговый синтез.

`R1-CODEX-004`. Проектный паспорт сеанса Codex обязан зафиксировать версию
Codex App, наблюдаемую модель и режим, рабочее дерево, применённые `AGENTS.md`,
разрешения, наличие сети и средств, редакцию Git и SHA-256 входной
спецификации. Это запись воспроизводимости, а не доказательство качества
модели.

### 6.3. Критика

`R1-CODEX-005`. Критика обязана ссылаться на точный архив и SHA-256 объекта,
проверять каждый критерий и делить замечания на:

- критические — блокируют приёмку;
- существенные — требуют преемника или явного решения пользователя;
- редакционные — не меняют смысл и могут быть вынесены за критический путь.

Результат критики: `accept`, `needs_rework` или `reject`, причина, покрытие
критериев, найденные противоречия, непроверенные утверждения и проект
следующего решения ядра.

`R1-CODEX-006`. Codex не выполняет переход состояния сам. Ядро проверяет
ссылку критики на архив и регистрирует решение отдельной операцией.

## 7. Договор полезного модуля Hermes

### 7.1. Граница модуля

`R1-HERMES-001`. Каждый модуль получает одну цель, один заранее определённый
раздел источников, явный запрет итогового синтеза, выходной предел и критерии
честного завершения.

`R1-HERMES-002`. DeepSeek V4 Flash остаётся основным кандидатом низового слоя.
Это решение относится к точной проектной связке и не является доказательством
пригодности любой версии модели или любого профиля Hermes.

`R1-HERMES-003`. План обязан однозначно выбрать один путь:

- **нативный:** Hermes использует собственный сохранённый доступ во временном
  проектном профиле;
- **посреднический:** ключом владеет отдельный доверенный посредник, а Hermes
  не имеет прямого доступа к поставщику.

Смешивать эти пути в одной попытке запрещено. Для первого R1 основным
кандидатом является нативный путь, уже спроектированный в
документе 135. Устаревший
комментарий `config/hermes-pipeline-profile.yaml` о ключе посредника должен
быть устранён реализацией до местной приёмки.

### 7.2. Содержание результата

`R1-HERMES-004`. Полезный модуль обязан вернуть обычный окончательный текст и
машиночитаемый указатель результата. В содержании для каждого существенного
утверждения должны присутствовать:

| Поле | Смысл |
|---|---|
| `source_id` | устойчивый идентификатор источника |
| `locator` | проверяемое место: путь и строки, раздел, страница либо прямой адрес |
| `claim` | утверждение без расширения за предел источника |
| `evidence` | достаточная выдержка или точный пересказ основания |
| `scope_boundary` | где вывод применим и где его перенос запрещён |
| `contradictions` | конфликтующие сведения либо `none_observed` |
| `uncertainty` | неизвестное, косвенное или неполное |
| `completion_state` | `completed`, `cannot_complete` или `truncated` |

`R1-HERMES-005`. `completed` допустим только при наличии всех обязательных
разделов и законченного последнего раздела. Признак ограничения длины,
оборванная фраза или отсутствующая часть дают `truncated`, а не успех.

`R1-HERMES-006`. `cannot_complete` является корректным исходом, если вход
недостаточен, противоречие неразрешимо, требуемое действие запрещено или
достаточный выход не помещается в утверждённый предел. Причина обязана быть
сохранена отдельно от гипотезы о причине.

### 7.3. Средства и подъём сложности

`R1-HERMES-007`. По умолчанию один модуль выполняется за один ход, без
модельных средств, навыков, памяти, автоматического повтора и запасной модели.
Иное поведение требует явного описания в Д24.

`R1-HERMES-008`. Более сильная модель внутри Hermes допускается только для
заранее признанного неделимого сложного задания либо после повторных
содержательных отказов на отдельных сопоставимых модулях. Подъём требует новой
редакции Д24 и решения пользователя; он не является повтором текущей попытки.

## 8. Принятая совокупная основа

`R1-BASE-001`. Техническое состояние `verified` не включает модуль в основу.
В неё входят только архивы заданий в состоянии `accepted`.

`R1-BASE-002`. Сборка основы обязана создать неизменяемый манифест со списком
модулей, архивных путей, SHA-256, редакций критериев и содержательных решений.

`R1-BASE-003`. Отдельная матрица покрытия обязана связать каждый критерий
спецификации с принятым утверждением и источником, а также перечислить
непокрытые критерии, противоречия и неизвестное.

`R1-BASE-004`. Основа считается допустимой для Claude Code только если:

1. все обязательные модули приняты;
2. критических противоречий нет либо способ их разрешения заранее задан;
3. каждый обязательный критерий покрыт; непокрытый обязательный критерий
   останавливает путь и требует новой редакции спецификации, а не устного
   исключения после исполнения;
4. повторная проверка SHA-256 архива успешна;
5. полный фактический вход Claude материализован до внешнего вызова.

`R1-BASE-005`. Рабочий файл Hermes, пересказ диалога, непринятый результат или
голая ссылка на недоступный файл не могут заменять архивную основу.

## 9. Договор полной роли Claude Code

### 9.1. Назначение и вход

`R1-CLAUDE-001`. Claude Code получает всю принятую основу и создаёт законченный
итоговый документ. Его роль включает разрешение явно заданных противоречий,
сведение ограничений, проверку внутренней согласованности и полное покрытие
спецификации.

`R1-CLAUDE-002`. Если средства чтения отключены, в запрос встраиваются полные
тексты всех принятых модулей, манифест, матрица покрытия, спецификация и
структура результата. Ссылка без содержимого считается отсутствующим входом.

`R1-CLAUDE-003`. До допуска вызова программа обязана измерить фактический
размер входа, требуемый выход и запас контекста. Исторические пределы 16 КБ на
вход и 4096 выходных токенов нельзя переносить в R1 без доказательства их
достаточности для точного сценария.

### 9.2. Связка и число обращений

`R1-CLAUDE-004`. Claude Code 2.1.206 + Z.ai + GLM-5.2 с усилием `high` является
наблюдавшимся кандидатом, но Д24 обязан зафиксировать фактическую версию,
модель, поставщика, настройки и SHA-256 проектного профиля на момент RUN.

`R1-CLAUDE-005`. Один ход оболочки не равен автоматически одному обращению к
поставщику. Служебные и вспомогательные обращения учитываются отдельно и не
могут превышать общий предел Д24.

Если оболочка или поставщик не позволяют достоверно определить число
обращений, Д24 обязан закрепить консервативный верхний предел по наблюдаемой
телеметрии либо заблокировать такую связку для R1. Неизвестное число нельзя
заменять предположением «один ход — один вызов».

`R1-CLAUDE-006`. Проектный режим обязан использовать отдельную настройку
процесса и не менять постоянные пользовательские настройки Claude Code.

### 9.3. Полный выход

`R1-CLAUDE-007`. Итог обязан:

- содержать все разделы утверждённой структуры;
- покрывать все обязательные критерии;
- сохранять ссылки на принятые источники и границы применимости;
- перечислять разрешённые и неразрешённые противоречия;
- отделять доказанное, ручное правило, предположение и отсутствующую функцию;
- завершаться явным разделом ограничений и контрольным листом применения.

`R1-CLAUDE-008`. Усечённый ответ, пустое содержимое, отсутствующий последний
раздел, ссылка на несуществующий источник или новое существенное утверждение
без основания блокируют содержательную приёмку. Автоматического повтора нет.

## 10. Сквозная доказательность и качество

`R1-QUALITY-001`. Обязательная цепочка имеет вид:

`критерий → модуль Hermes → утверждение → источник и место → принятая редакция
→ раздел итога Claude → замечание Codex → решение пользователя`.

`R1-QUALITY-002`. Автоматическая проверка подтверждает существование ссылки,
целостность, допустимый путь, полноту обязательных полей и связь редакций. Она
не объявляет утверждение истинным.

`R1-QUALITY-003`. Содержательная оценка проводится до раскрытия расчётной
стоимости. Цена участвует в выборе только между результатами практически
сопоставимого качества.

`R1-QUALITY-004`. Неполные сведения о токенах или подписочной квоте
сохраняются как неполные. Расчётный эквивалент по тарифу не называется
фактическим списанием.

`R1-QUALITY-005`. Приёмка основы и приёмка итогового документа являются двумя
разными решениями, каждое связано со своей точной редакцией и ведомостью.

`R1-QUALITY-006`. Пользователь может принять остаточное ограничение явно, но
система не вправе превращать отсутствие проверки в положительный результат.

регламент допуска, исполнения, остановки, приёмки и завершения первого
рабочего применения конвейера. Это продолжает полезную цель
этапа 4 плана 118, но исправляет
измеренную ошибку одного слишком крупного задания Hermes.

### 11.2. Неизменяемый граф

### 11.3. Разделение источников

- **M1** получает программу ядра, схемы договоров, описание автомата и

- **M2** получает только договоры, проектные профили, переходники и измеренные
  отчёты Hermes и Claude Code.
- **M3** получает эксплуатационный профиль 1.2, правила качества, отчёты
  отказов и документы остановки/закрытия.

Каждый файл и фрагмент закрепляется путём, редакцией Git и SHA-256. Пересечение
допускается только для общего нормативного фрагмента, если оно заранее
перечислено в Д24. Модель не выбирает собственный пакет источников.

## 12. Состояния и последовательность переходов

Спецификация использует действующий компактный автомат и не добавляет
смысловые состояния `planning`, `assembling` или `critiquing`.

### 12.1. Проект и RUN

1. проект создаётся в `active`;
2. RUN создаётся в `active` после запечатывания графа;
3. после принятого итога RUN переходит в `report_ready`;
4. пользовательское принятие даёт `content_accepted`;
5. окончательная операция ядра даёт `closed`;
6. проект проходит `awaiting_final_acceptance → completed` либо остаётся
   `active` при доработке.

### 12.2. Задание и попытка

Для каждого модельного задания:

`task ready → active → result_submitted → verified → accepted`;

`attempt active → result_submitted → verified`.

`verified` означает только техническую целостность. Содержательное решение
создаёт `accepted` либо `needs_rework`. Повторное исполнение не возвращает
старую попытку в `active`: создаётся точечное задание-преемник после отдельного
решения и, если меняется Д24, новой редакции плана.

`R1-OPS-001`. Зависимое задание не может перейти из `ready` в `active`, пока
все указанные предшественники не находятся в `accepted` и Д24 не действует.

## 13. Остановка, отказ и восстановление

| Событие | Обязательное действие | Что запрещено |
|---|---|---|
| вход отсутствует или превышает предел | остановить до вызова, записать точную причину | сокращать вход без новой редакции |
| оболочка завершилась до результата | сохранить код, поток ошибок, неполный расход и проверяемые факты | приписывать отказ модели без доказательства |
| ответ усечён | технический либо содержательный отказ по договору | объявлять частичный текст успехом |
| модуль не принят | остановить зависимый путь | запускать Claude или повторять автоматически |
| Д24 истёк/исчерпан | блокировать новые внешние действия | использовать остаток прежнего разрешения |
| поздний результат | поместить в карантин и сохранить событие | менять состояние задания задним числом |
| остановка процесса | восстановить состояние из SQLite, событий и архивов | угадывать состояние по диалогу |
| требуется доработка | сохранить старый архив, создать ограниченного преемника | редактировать принятый результат |

`R1-OPS-002`. Один доказанный местный программный дефект допускает одно
исправление и местную проверку без модельного вызова. Исправление не разрешает
повтор прежнего внешнего действия.

`R1-OPS-003`. Содержательный отказ связки ведёт к остановке, смене кандидата
или новому отдельно утверждённому заданию, а не к цепочке микропроверок.

`R1-OPS-004`. Причина отказа хранится как наблюдаемый факт; предполагаемая
причина — отдельным полем с уровнем уверенности.

`R1-OPS-005`. Закрытие не стирает активный или неопределённый расход. Он
закрывается подтверждённым, расчётным, нулевым либо неопределённым исходом.

## 14. Безопасность и изоляция профилей

`R1-SEC-001`. Секреты находятся только в хранилище соответствующей оболочки
или среде процесса. Они не входят в Д24, запрос, архив, журнал, снимок,
диагностику и Git.

`R1-SEC-002`. Проектный запуск Hermes использует временный `HERMES_HOME`, не
читает и не меняет личные навыки, память и настройки самостоятельного Hermes.

`R1-SEC-003`. Проектный запуск Claude Code использует изолированную настройку
процесса. Постоянный пользовательский `settings.json` не изменяется
автоматически.

`R1-SEC-004`. Средства, сеть и запись запрещены по умолчанию. Разрешение
задаётся белым списком конкретного задания и входит в SHA-256 Д24.

Для нативного пути Hermes штатное обращение оболочки к закреплённому поставщику
считается разрешённым транспортом. Оно не разрешает модели средства сети или
произвольные внешние действия. Если ограничение процесса только конечной
точкой поставщика технически не обеспечено, этот остаточный риск явно входит
в Д24 и итоговый отчёт; его нельзя выдавать за силу посреднической изоляции.

`R1-SEC-005`. Результат может быть опубликован только внутри каталога попытки;
пути с выходом за границу, абсолютные и сетевые пути отвергаются.

## 15. Местная проверка до первого модельного вызова

Реализация в `main` не допускается к полезному RUN, пока не пройдёт один
целевой набор местных проверок.

`R1-TEST-001`. Схема Д24 принимает полный допустимый план и отвергает отсутствие
любой обязательной группы полей.

`R1-TEST-002`. Канонический SHA-256 одинаков для семантически одинакового
документа и меняется при любом значимом изменении.

`R1-TEST-003`. Подтверждение связано с одним RUN, редакцией, суммой, числом
вызовов и сроком; перенос и повтор не расширяют полномочия.

`R1-TEST-004`. Ядро блокирует незапланированный, лишний, просроченный и
превышающий предел вызов, включая служебное обращение оболочки.

`R1-TEST-005`. Договор Codex проверяет идентификаторы критериев, точный объект
критики, SHA-256 и допустимое решение без прямой записи состояния.

`R1-TEST-006`. Договор Hermes проверяет восемь полей доказательства, конечную
метку, отсутствие усечения и единственный выбранный сетевой путь.

`R1-TEST-007`. Сборщик основы принимает только `accepted`, повторно проверяет
архивы и создаёт полную матрицу покрытия.

`R1-TEST-008`. Предварительная проверка Claude отклоняет ссылку без текста,
неполный архив, недостаточный контекст, недостаточный выходной предел и
неучтённое дополнительное обращение.

`R1-TEST-009`. Искусственный сквозной сценарий без моделей проходит все
реальные состояния, зависимости, остановку, поздний пакет, восстановление и
окончательное решение пользователя.

`R1-TEST-010`. Проверка секретов и путей подтверждает, что личные настройки
Hermes и Claude Code, ключи и данные других попыток недоступны.

Один общий прогон существующих проверок выполняется после целевого набора.
Расширение испытаний допускается только при конкретном сбое, а не для
бесконечной шлифовки уже подтверждённой функции.

## 17. Последовательность реализации в `main`

После отдельного принятия настоящей спецификации работа в `main` должна идти
одной серией без модельных вызовов:

1. создать схему и хранение Д24, запечатывание, подтверждение и учёт вызовов;
2. добавить договоры постановки и критики Codex;
3. добавить проверяемый договор полезного модуля Hermes и устранить
   неоднозначность проектного профиля;
4. добавить сборщик принятой основы и матрицу покрытия;
5. расширить предварительную проверку Claude Code до фактического полного
   входа и требуемого выхода;
6. реализовать один последовательный координатор точного графа раздела 11;
7. выполнить проверки раздела 15 и один общий местный прогон;
8. показать пользователю отчёт готовности и точный проект Д24;
9. только после нового разрешения создать полезный RUN и выполнить цикл.

Новые промежуточные RUN, отдельные испытания каждой мелкой функции и модельные
вызовы до пункта 9 запрещены. Если реализация обнаружит противоречие
спецификации, сначала обновляется настоящий документ и создаётся новая
редакция, а не вводится скрытое поведение.

## 18. Условия готовности спецификации к реализации

Спецификация готова стать входом в `main`, если пользователь подтвердил, что:

1. граница R1 соответствует полезной цели продукта;
2. одно решение по Д24 заменяет микроподтверждения, но не ослабляет контроль;
3. три модуля Hermes не подменяют полную роль Claude Code;
4. качество и доказательность первичны, расход вторичен;
5. точный сценарий раздела 11 действительно полезен проекту;
6. реализация выполняется сначала местно, одним ограниченным этапом;
7. настоящий документ не является разрешением на RUN или модельный вызов.

До такого решения документ остаётся нормативным проектом редакции 1.0.
