# Гипотеза повышения качества за счёт разных агентных оболочек и моделей LLM

> **Примечание к публикационной копии.** Внешние источники и связи с
> включёнными документами сохранены. Ссылки на закрытую память, рабочие RUN,
> код и документы вне публикационного комплекта заменены текстовыми
> указателями; соответствующие закрытые файлы не опубликованы.

**Дата:** 25 июля 2026 года

**Состояние:** проверяемая проектная гипотеза; не доказанный эффект

**Связанные документы:** критическая оценка схемы, [сравнение с Orca](59-orca-comparison.md), [сравнение с oh-my-pi](68-oh-my-pi-comparison.md), [реестр литературы](159-research-foundations-and-external-sources-register.md), план качества.

## 1. Назначение

Документ объясняет, почему разделение одной сложной аналитической работы между
несколькими точными связками «модель + поставщик + агентная оболочка + версия +
настройки + договор» **может** повысить качество итогового ответа.

Ключевое слово — «может». Ни внешняя литература, ни текущие RUN проекта пока
не доказывают, что именно сочетание Codex App, Hermes Agent и Claude Code с
выбранными моделями превосходит одну сильную модель. Синергия остаётся
гипотезой D-214 и должна проверяться по D-150.

## 2. Формулировка основной гипотезы

> Если сложная доказательная задача разделена на непересекающиеся роли, каждая
> роль выполняется подходящей точной связкой модели и агентной оболочки, ошибки
> связок не полностью совпадают, а переходы между ролями проходят через
> независимую содержательную приёмку и детерминированные проверки, то итоговый
> ответ будет полнее, фактически точнее, лучше связан с источниками и реже
> содержать критические пропуски, чем ответ одной сильной связки при
> сопоставимом задании.

Гипотеза составная. Она верна только при одновременном выполнении пяти
условий:

1. роли действительно различаются, а не повторяют одну и ту же работу;
2. выбранная связка пригодна для своей роли;
3. ошибки участников достаточно различны;
4. проверяющий способен обнаруживать ошибки исполнителя;
5. передача материалов не теряет контекст и не закрепляет ошибку как факт.

Если хотя бы одно условие не выполнено, многооболочечная схема может не дать
прироста или оказаться хуже одиночной.

## 3. Единица оценки

В проекте нельзя оценивать модель отдельно от среды исполнения. Правильная
единица:

```text
связка = модель
       + поставщик и конечная точка
       + агентная оболочка
       + версии
       + системные инструкции
       + режим рассуждения
       + доступные средства
       + способ передачи контекста
       + пределы входа и выхода
       + договор результата
```

Одна и та же модель в разных оболочках может получить иной системный текст,
набор средств, цикл вызова, управление контекстом, правила продолжения и
обработку ошибки. Поэтому показатель модели из общей оценки не доказывает
качество её точной связки с Hermes, Claude Code или Codex App.

## 4. Предполагаемые механизмы прироста

### 4.1. Специализация ролей

Один участник не должен одновременно искать факты, разрешать все
противоречия, строить окончательный документ и оценивать собственный ответ.
Проект разделяет работу:

| Роль | Основной вклад в качество | Главная граница |
|---|---|---|
| Codex App + сильная модель | постановка задачи, договор качества, независимая приёмка и критика | не подменяет массовое извлечение доказательств |
| Hermes + модель-исполнитель | извлечение и анализ ограниченных групп источников, проверяемые карточки доказательств | не пишет весь итоговый документ вместо оркестратора |
| Claude Code + модель-оркестратор | полная оценка принятой основы, согласование блоков, устранение противоречий, законченный ответ | не владеет официальными состояниями |
| Детерминированное ядро | целостность, права, состояния, порядок, остановка и воспроизводимость | не решает, истинно ли содержательное утверждение |

Специализация снижает число конкурирующих целей в одном запросе. Но она
помогает только тогда, когда границы ролей точны, а передаваемый материал
достаточен для следующей роли.

### 4.2. Различие ошибок моделей

Разные семейства моделей обучены и настроены неодинаково. Возможный выигрыш
возникает не из самого факта различия названий, а из того, что участники могут:

- замечать разные пропуски;
- по-разному разрешать неоднозначность;
- не повторять одну и ту же галлюцинацию;
- компенсировать слабые места друг друга.

[Diversity Empowers Intelligence](https://openreview.net/pdf?id=cKlzKs3Nnb)
поддерживает связь между разнообразием и выигрышем, но проект должен измерить
именно несовпадение ошибок своих связок. Если ошибки коррелированы, различие
моделей почти бесполезно.

### 4.3. Различие агентных оболочек

[Harness-Bench](https://arxiv.org/html/2605.27922v1) рассматривает
взаимодействие модели и оболочки как отдельный фактор. В проекте оболочки
различаются способом удержания инструкций, средствами, рабочим циклом,
доступом к файлам, продолжением сеанса и обработкой результата.

Потенциальный положительный эффект состоит в том, что одна оболочка лучше
поддерживает постановку и критику, другая — длительную оркестрацию документа,
третья — ограниченное исполнение низовых заданий. Однако различие оболочек
может породить и рассогласование форматов, потерю контекста или несовместимые
правила. Следовательно, сам факт трёх оболочек не является преимуществом.

### 4.4. Асимметрия «исполнитель — сильный проверяющий»

[Small LMs Need Strong Verifiers](https://aclanthology.org/2024.findings-acl.924.pdf)
и работы по weak-to-strong обосновывают проверку результата более сильным
участником. Это поддерживает использование быстрой модели для ограниченных
модулей Hermes при условии полноценной проверки Codex.

Но возникает узкое место отбора: если проверяющий не различает правильный и
ошибочный материал, слабый ответ получает ложное доверие. Поэтому
[Selection Bottleneck](https://arxiv.org/html/2603.20324) является прямым
ограничением гипотезы.

### 4.5. Независимая проверка вместо самооценки

Модель склонна защищать собственную линию рассуждения и повторять исходные
ошибки. Передача результата другой связке создаёт возможность независимой
критики. Эффект существует только при трёх условиях:

1. критик получает первичные доказательства, а не только пересказ;
2. ему не раскрывают желаемый вердикт;
3. окончательная оценка не принадлежит той же модели, чей ответ сравнивается.

GPT не должен быть единственным судьёй собственного варианта. Для D-150 нужна
слепая человеческая оценка или отдельный проверяющий, не участвующий в
создании сравниваемых ответов.

### 4.6. Детерминированные границы уменьшают каскад ошибок

Orca, oh-my-pi и рекомендации Anthropic независимо сходятся к
детерминированному управлению потоком. В проекте модельный результат не
передаётся дальше только потому, что запрос технически завершился. Ядро
проверяет договор и целостность, Codex принимает содержание, после чего
неизменяемая копия становится входом следующей роли.

Это не доказывает истинность принятого утверждения, но уменьшает вероятность
тихой передачи неполного, повреждённого или неподтверждённого результата.

## 5. Что действительно подтверждают Orca и OMP

[Исследование Orca](59-orca-comparison.md) и
[исследование oh-my-pi](68-oh-my-pi-comparison.md) подтверждают ограниченный
архитектурный вывод:

- устойчивые агентные системы выносят официальные переходы из LLM в код;
- жизненный цикл процессов, изоляция, контекст и одобрения являются частью
  качества связки;
- ошибки оболочки способны обесценить сильную модель;
- удобство и автономность без строгих границ создают отдельные риски.

Они **не подтверждают**, что разные модели в разных оболочках дают лучший
аналитический ответ. Orca оркестрирует внешние средства программирования, а
oh-my-pi является самостоятельным агентом программирования. Их предмет,
пользователи и показатели отличаются от текущего проекта.

## 6. Контраргументы и условия провала

### 6.1. Одна сильная модель может быть лучше

[Rethinking Mixture-of-Agents](https://arxiv.org/abs/2502.00674) показывает,
что несколько выборок одной сильной модели с последующим объединением могут
превосходить неоднородную группу. По мере усиления моделей преимущество
многоагентности также сокращается. Поэтому одиночная сильная связка является
обязательным, а не формальным вариантом сравнения.

### 6.2. Каскадная ошибка может усилиться

Если Codex принимает неверную основу, Claude Code получает ошибку уже как
доверенный вход. Дополнительный этап тогда не исправляет, а укрепляет дефект.
Количество ролей увеличивает число границ, на которых возможны потеря смысла,
неверное сокращение и конфликт инструкций.

### 6.3. Разнообразие может быть только внешним

Разные названия моделей не гарантируют разные ошибки. Модели могут опираться
на сходные данные, одинаковые распространённые ответы и одинаковые шаблоны
рассуждения. Разные оболочки также могут передавать почти одинаковый системный
контекст. Такое разнообразие не создаёт независимой проверки.

### 6.4. Оркестратор может стать слабейшим звеном

Если модель Claude Code плохо отбирает, сопоставляет или разрешает
противоречия, качество полной основы не превратится в качественный итог.
Полноценную роль оркестратора нельзя сокращать до краткой проверки ради цены.

### 6.5. Дополнительный расход не равен дополнительному качеству

Большее число токенов и вызовов может создавать повтор, многословие и новые
ошибки. Цена и задержка фиксируются, но сначала сравнивается качество. Более
дешёвый вариант предпочтителен только при практически сопоставимом качестве.

## 7. Проверяемые следствия гипотезы

| Код | Предсказание | Что его опровергает |
|---|---|---|
| H1 | целевая схема повышает фактическую точность и полноту относительно сильной одиночной связки | отсутствие практически значимого прироста или ухудшение хотя бы одного критического показателя |
| H2 | критика другой связкой обнаруживает больше реальных дефектов, чем самооценка создавшей ответ модели | ложные замечания растут, а доля найденных подтверждённых ошибок не увеличивается |
| H3 | выигрыш выше на задачах, где ошибки участников различаются | качество не связано с измеренным несовпадением ошибок |
| H4 | роль исполнителя может использовать более быструю модель без снижения качества итогового ответа | пропуски исполнителя проходят приёмку или требуют дорогой повторной переработки |
| H5 | структурированная передача принятой основы уменьшает потерю доказательств | итог содержит меньше проверяемых ссылок либо больше неподтверждённых обобщений, чем одиночный вариант |
| H6 | разные оболочки дают воспроизводимо разные результаты одной модели на одинаковом задании | различия не превышают обычный разброс повторных запусков одной связки |

H6 проверяется только там, где одна и та же модель действительно доступна в
сопоставимых оболочках. Показатели модели нельзя подменять таким опытом.

## 8. Минимальная проверка D-150

### 8.1. Сравниваемые варианты

1. **Сильная одиночная связка:** Codex App + GPT выполняет задачу целиком.
2. **Повтор одной связки:** несколько независимых ответов той же сильной
   связки с заранее определённым способом объединения. Это проверяет, не
   объясняется ли выигрыш просто дополнительным вычислением.
3. **Ролевая схема без доказанного разнообразия:** по возможности одна модель
   выполняет несколько ролей при сохранении договоров. Этот вариант отделяет
   пользу декомпозиции от пользы разных моделей.
4. **Целевая схема:** Hermes + исполнитель → содержательная приёмка Codex →
   Claude Code + оркестратор → независимая критика → итог.

Если технически невозможно получить все четыре варианта с сопоставимыми
версиями, недоступная ячейка помечается как отсутствующая. Её нельзя заменять
выводом из общего показателя модели.

### 8.2. Одинаковые условия

- один и тот же исходный пакет источников;
- один предмет задачи и один договор полезного результата;
- одинаковые запреты на внешние сведения;
- закреплённые версии моделей, поставщиков, оболочек и настроек;
- заранее определённые пределы выхода, достаточные для полного ответа;
- отсутствие автоматического повтора после содержательного отказа;
- сохранение всех входов, выходов и доказательств расхода.

### 8.3. Первичные показатели качества

1. фактическая правильность;
2. полнота обязательных вопросов;
3. проверяемость ссылок и соответствие утверждения источнику;
4. корректность границ применимости;
5. выявление и разрешение противоречий;
6. соблюдение договора и структуры;
7. число критических ошибок;
8. полезность итогового решения для пользователя.

Цена, токены и время являются вторичными показателями. Они участвуют в
выборе только после установления практически сопоставимого качества.

### 8.4. Оценка

- ответы обезличиваются и перемешиваются;
- оценщик не знает, какая схема создала вариант;
- GPT, участвовавший в подготовке ответа, не является единственным судьёй;
- критические факты сверяются с первичными источниками;
- разногласия оценщиков и неопределённость сохраняются;
- критерий успеха и допустимая разница задаются до просмотра результатов.

Для общего вывода нужен набор реальных задач нескольких типов, а не один
показательный RUN. Один RUN может проверить работоспособность пути, но не
синергию.

## 9. Критерий принятия или отклонения

Гипотеза получает предварительную поддержку, если целевая схема:

1. превосходит сильную одиночную связку по заранее выбранному совокупному
   показателю качества;
2. не увеличивает число критических ошибок;
3. сохраняет или улучшает доказательную трассировку;
4. показывает повторяемый эффект на нескольких задачах;
5. объясняет выигрыш измеренным различием ошибок или вкладом конкретной роли.

Если качество практически сопоставимо, гипотеза о повышении качества не
подтверждается. Тогда цена, время и простота могут стать основанием выбора
одиночной или более простой схемы.

Если многооболочечная схема хуже, проект должен упростить роли, заменить
слабую связку или отказаться от необоснованной многомодельности. Архитектура
не должна защищаться от отрицательного результата опыта.

## 10. Текущий статус применительно к проекту

| Утверждение | Статус |
|---|---|
| оболочка влияет на поведение модели | поддержано внешними исследованиями в общем виде |
| детерминированное ядро предпочтительнее передачи состояний LLM | поддержано внешними руководствами, Orca, oh-my-pi и местной реализацией |
| сильный проверяющий может улучшить работу более слабого исполнителя | поддержано литературой, но зависит от качества отбора |
| разные модели обязательно лучше одной | не подтверждено; есть сильные контраргументы |
| ошибки точных связок проекта различаются | не измерено |
| GLM или иная модель Claude Code является достаточным оркестратором | смешанное наблюдение RUN-025: длинный синтез завершён, но принят только после независимой финализации Codex |
| DeepSeek V4 Flash пригоден для ограниченных модулей Hermes | RUN-025 дал принятые M1–M3 при одной точной конфигурации и сохранил измеренный отказ первоначального M3 |
| вся целевая схема повышает качество относительно Codex + GPT | не проверено по D-150 |

## 11. Практическое следствие до D-150

До проверки не следует менять роли по одному внешнему обзору или объявлять
тройку доказанно лучшей. Действует следующий порядок:

1. считать RUN-025 первым завершённым полезным последовательным циклом, но не
   переносить его результат за пределы точной конфигурации;
2. сохранить DeepSeek V4 Flash основной моделью ограниченного исполнительского
   слоя Hermes;
3. сохранить за Claude Code полноценную роль подготовки законченного
   документа;
4. сохранить за Codex постановку, содержательную приёмку и независимую
   критику;
5. после работоспособного цикла провести отдельное сравнение D-150;
6. добавлять новые компоненты только против измеренных классов ошибок.

## 12. Источники и границы

Ключевые источники перечислены в разделах 4–6. Полный внешний указатель с
идентификаторами S-* находится в
[документе 159](159-research-foundations-and-external-sources-register.md).

Orca и oh-my-pi используются как внешние инженерные сравнения, а не как
академическое доказательство синергии. Свежие работы arXiv используются как
препринты с указанными ограничениями. Точная связка проекта оценивается только
